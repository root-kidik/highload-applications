## Пакетная обработка

### Сервисы (онлайновые системы)

- модель общения: запрос -> ответ
- мера производительности: время отклика

### Системы пакетной обработки (автономные системы)

- модель общения: большое количество данных -> задача -> обработанные данные
- мера производительности: пропускная способность

### Системы поточной обработки (системы почти реального времени)

- модель общения: большое количество данных -> обработанные данные
- мера производительности: время отклика

## MapReduce и распределенные файловые системы

3 стадии:

- Map: преобразует входные данные в пару [ключ; значение]
- Shuffle & Sort: группировка и сортировка данных по одному и томуже ключу
- Reduce: агреггируют данные по ключам

### Пример

Разберем все 3 шага MapReduce на практическом e-commerce кейсе: подсчете количества обновлений для каждого товара по сырым логам.

**Входные данные**
Три параллельных воркера читают сырые логи с разных серверов:

* Воркер 1: `["item_101", "item_102"]`
* Воркер 2: `["item_101", "item_103"]`
* Воркер 3: `["item_101", "item_102"]`

---

**1. Шаг Map (Преобразование)**
Каждый воркер локально читает свои строки и превращает каждую запись в пару `[Ключ, Значение]`. Здесь ключ - это ID товара, а значение - единица.

* Воркер 1 выдает: `("item_101", 1)`, `("item_102", 1)`
* Воркер 2 выдает: `("item_101", 1)`, `("item_103", 1)`
* Воркер 3 выдает: `("item_101", 1)`, `("item_102", 1)`

---

**2. Шаг Shuffle & Sort (Перемешивание и Сортировка)**
Этот шаг автоматически выполняет сам фреймворк MapReduce. Он пересылает пары по сети так, чтобы **все одинаковые ключи попали на один и тот же редьюсер**, после чего сортирует их по ключу.

Фреймворк формирует структуры вида `(Ключ, [Список значений])`:

* На Редьюсер 1 уходит: `("item_101", [1, 1, 1])`
* На Редьюсер 2 уходит: `("item_102", [1, 1])`
* На Редьюсер 3 уходит: `("item_103", [1])`

---

**3. Шаг Reduce (Сворачивание / Агрегация)**
Каждый редьюсер берет свой ключ и список его значений, выполняет над ними целевую операцию (в данном случае - сумму `SUM()`) и записывает результат в файл.

* Редьюсер 1: `item_101` $\rightarrow$ $1 + 1 + 1 = 3$ $\rightarrow$ **`("item_101", 3)`**
* Редьюсер 2: `item_102` $\rightarrow$ $1 + 1 = 2$ $\rightarrow$ **`("item_102", 2)`**
* Редьюсер 3: `item_103` $\rightarrow$ $1 = 1$ $\rightarrow$ **`("item_103", 1)`**

---

**Итоговый файл результатов (Output)**

```text
item_101: 3
item_102: 2
item_103: 1

```

### Локальность данных (Data Locality)

Принцип `код к данным`: 
В `HDFS` файлы режутся на крупные блоки (`64–128 МБ`) и распределяются по кластеру. 
Чтобы не качать терабайты по сети, планировщик `MapReduce` запускает `Map-задачу` физически на той машине, где лежит нужный блок `HDFS`.

### Паттерны соединения данных (Joins)

Соединение двух наборов данных (например, логов просмотров и каталога товаров) - самая частая и тяжелая операция:

- `Reduce-side join` (`Sort-Merge Join`): 
Оба набора данных партиционируются по ключу соединения и сортируются в фазе `Shuffle`. 
`Редьюсер` получает сводный поток с одним ключом. Подходит для двух огромных таблиц, но создает огромную нагрузку на сеть.

- `Map-side join` (`Broadcast Hash Join`): 
Если одна таблица маленькая (например, справочник категорий товаров), она целиком загружается в память каждого маппера. 
Соединение происходит на этапе `Map` вообще без фазы `Shuffle`.

- `Partitioned Hash Join`: 
Если обе таблицы огромны, но заранее отпартиционированы по одному и тому же ключу, маппер может соединять только соответствующие парные блоки.

### Проблема перекоса данных (Data Skew / Hotspotting)

- Проблема: 
Если у вас есть один `горячий ключ` (например, категория с миллионами товаров или популярный бренд), все данные по нему придут на один редьюсер. 
Он будет считаться часами, пока остальные узлы простаивают.

- Решение: 
Использование `Combiners` (предварительное сжатие данных на маппере) и техники `Salting` (добавление случайной `соли` к ключу для размазывания нагрузки по нескольким редьюсерам с последующей повторной агрегацией).

### Промежуточное состояние (Intermediate State) и переход к DAG

- Главный недостаток `MapReduce`: 
Одной пары `Map-Reduce` никогда не хватает. 
Сложные пайплайны состоят из цепочек в `10–20` `MapReduce-задач`. Каждая задача сбрасывает промежуточный результат на диск (`HDFS`) с тройной репликацией.

- Эволюция в `Dataflow Engines` (`Spark`, `Tez`, `Flink`): 
Вместо жесткой цепочки отдельных задач они строят единый `DAG` (Направленный ациклический граф). 
Промежуточные данные передаются напрямую из оперативной памяти одного узла в память другого по сети, без материализации на диск, а при сбоях просто пересчитываются по графу вычислений (`Lineage`).

### Результаты пакетной обработки (Output of Batch Workflows) 

Зачем мы вообще запускаем пакетную обработку и куда девать результат?

- `Поисковые индексы` (`Search Indexes`): 
Построение инвертированного индекса - классическая задача для `MapReduce`. 
Вместо того чтобы построчно отправлять товары в поисковый движок через `API`, пакетная задача генерирует готовые статичные файлы-сегменты (например, `Lucene index`) и загружает их прямо на поисковые машины.

- `Запись в базами данных` (`Key-Value Stores`): 
Делать `INSERT` или `UPDATE` из тысяч мапперов/редьюсеров напрямую в онлайн-БД нельзя - это убьет БД сетью и блокировками. 
Правильный паттерн: пакетный процесс создает файлы базы данных прямо на диске (например, `SSTables`) и загружает их целиком одним батчем (`Bulk Loading`).

- Концепция `Derived Data` (Производные данные): 
Входные данные для батча всегда неизменяемы (`Raw Logs`, `Immutable events`). 
Выход пакетной задачи - это материализованное представление (`Materialized View`). 
Если в коде обнаружат баг, не нужно чистить БД сложными миграциями - достаточно просто удалить старый результат и пересчитать пайплайн заново.

### MapReduce vs Распределенные базы данных (MPP)

| Критерий | MPP Базы Данных (например, Greenplum, Vertica) | MapReduce / Spark |
| --- | --- | --- |
| **Схема данных** | **Schema-on-write**: структура данных проверяется строго при записи в БД. | **Schema-on-read**: данные хранятся в сыром виде (JSON, логи), а структура накладывается во время выполнения кода. |
| **Реакция на сбои** | Если 1 из 100 машин падает во время вычисления, весь запрос отменяется и перезапускается. | При падении узла перезапускается **только упавшая таска** на другой машине. |
| **Обработка кода** | Ограничена возможностями SQL и встроенных функций. | Произвольный код на любом языке программирования. |

### Вторичная сортировка (Secondary Sort)

- Проблема: 
Фаза `Shuffle` сортирует пары по ключу, но внутри массива значений для этого ключа порядок случайный.

- Задача: 
Например, нужно получить события пользователя `user_id`, строго отсортированные по времени `timestamp`. 
Если собрать все события пользователя в памяти `редьюсера` и отсортировать там - при крупном пользователе случится `Out of Memory` (`OOM`).

- Решение: 
Использование составного ключа (`user_id, timestamp`). 
Фаза группировки отправляет все записи с одинаковым `user_id` на один `редьюсер`, но фаза сортировки уже упорядочивает их по `timestamp` до попадания в `редьюсер`.

### Итеративная и графовая обработка (Bulk Synchronous Parallel / Pregel)

- Ограничение `DAG`:
В `Spark` или `Tez` вычисления идут строго от входа к выходу без петель. 
Но алгоритмы на графах (например, `PageRank` или поиск связей в соцсетях) требуют итеративной работы: алгоритм крутится в цикле, пока данные не сходятся к результату.

- Модель `BSP`: 
Для таких задач используется акторная модель на кластере (система `Pregel` от `Google`). 
Ноды обмениваются сообщениями и итерируются по шагам (`supersteps`) без постоянной материализации графа на диск.
